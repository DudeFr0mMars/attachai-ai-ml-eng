# Design notes

These notes distinguish implemented work from optional work not attempted.

## Part 2 — multi-turn session flow

The session flow now commits a pending booking and `PaymentAttempt(status="initiated")` before its first provider call, using the stable key `f"session:{session.id}"`. Direct confirmation similarly claims `f"booking:{booking.id}"` before charging. A replay returns a completed attempt or calls the provider's lookup with the same key; it never issues another charge for an existing initiated/unknown attempt. The mock provider remembers keyed outcomes during a process lifetime, so a simulated crash after charge can be reconciled on retry. If that volatile outcome is lost, the route returns HTTP 504 and requires external/manual reconciliation; it does not risk a second charge. This is at-most-once protection, not guaranteed automatic recovery. The direct booking route also rejects any caller amount that differs from the booking's stored `amount_cents` and charges only that stored value. Session-created bookings have no independent server-side quote in the existing schema or flow, so this amount fix deliberately covers existing bookings only, as agreed with the user.

## Part 2 — knowledge isolation fix

`app/routers/knowledge.py` first verifies that the URL club matches the authenticated member's club, then filters `KnowledgeChunk.club_id == member.club_id` in SQL before cosine-distance ordering and `limit(5)`. Filtering after the limit was rejected: an Oakhurst chunk could occupy one of the five slots and displace a valid Riverside result even if removed from the final response. The regression test places a more similar Oakhurst chunk in the database and asserts that the response contains only the Riverside chunk; the seeded-database before/after trace is in `TERMINAL_LOG.md`.

## Part 3 — structured extraction pipeline

**Status:** Implemented and exercised through the real OpenAI API on seeded PostgreSQL and `eval/golden_set.json`. The endpoint is `POST /clubs/{club_id}/extract-attributes` with `{"message_ids": [...]}`. It accepts only a same-club admin/service caller. Each message is resolved under the requested club before any LLM call, and its failure is returned in its own result entry without ending the batch. No tables, columns, or migrations were added.

### Idempotency

**Exact processed-message key in code:** `processed_key = MemberAttribute.source_message_id == message.id` in `app/routers/extraction.py`. Existing rows for that key yield `already_processed`; the original nine seeded messages already have such rows and are therefore skipped. A PostgreSQL transaction-level advisory lock on `message_id` serializes concurrent checks and writes. This gives row-level **idempotency** for nonempty results and prevents duplicate rows on replay, as the second real batch run shows. A zero-attribute extraction writes no row, so a replay may call the API again but still creates no duplicates. A durable marker for completed-empty messages would require schema ownership approval; I would raise adding a processed-message marker with the schema owner rather than add a table or column unilaterally.

### Restricted attributes and matching

**Actual check and location:** `build_member_profile_text` in `app/services/matching_service.py` filters `MemberAttribute.restricted.is_(False)` together with the member and club IDs before joining text. `rank_candidates` calls that builder for both the requester and every candidate and embeds those filtered strings at request time; it deliberately does not score from stored `profile_embedding` values because legacy vectors may contain restricted data. `refresh_member_embedding` uses the same builder for future stored vectors; the introduction endpoint independently applies `MemberAttribute.restricted.is_(False)` before composing `reason_text`. The extractor asks the model to flag health/clinical/psychometric content and `enforce_restricted` conservatively overrides a false flag when the source message or attribute contains explicit sensitive terms. Restricted rows are saved in the shared table but never reach the matching text/vector path. The seeded real-API demo wrote a therapy attribute as restricted and confirmed that text was absent from the matching profile.

### Retry strategy and batch failures

**Implemented retry strategy:** `OpenAIAttributeExtractor.extract` makes up to three attempts for HTTP 429, any 5xx, timeout, or transport failure. It sleeps with exponential backoff (base 0.5 seconds, doubling, capped at 4 seconds) plus up to 0.25 seconds of jitter; other 4xx and invalid structured outputs fail immediately. The route rolls back only the failing message's transaction, adds `status="failed"`, and continues. In the five-message test, messages 1–2 commit, message 3 raises a permanent failure and inserts nothing, then message 4 commits successfully and message 5 follows. The result statuses are `processed, processed, failed, processed, processed`. API retries can repeat a model call after an ambiguous transport failure, but the database lock/check prevents duplicate attribute rows on request replay.

Payment idempotency for issue 4 uses stable payment-operation keys. Part 3 extraction idempotency needs its own processed-message key. They share the principle of safe retries, but a payment key does not establish whether a message's attributes were extracted, and the LLM retry strategy remains pending until Part 3 is implemented.

### Authorization, eval, and threshold

**Authorization:** `caller.role in {"admin", "service"}` and `caller.club_id == club_id` are required before the batch. Each message query also filters `ConversationMessage.club_id == club_id`, so an out-of-club ID produces `not_found` without sending its body to the LLM. Tests cover member and foreign-admin rejection.

**Eval:** `scripts.eval_extraction` calls the same real OpenAI extractor on every `eval/golden_set.json` message, with no test double or DB writes. A record passes only when one extracted attribute has the expected kind, exact restricted flag, and at least one expected keyword. The threshold is 75% (at least 3 of 4 complete records), with an additional fail-closed gate requiring every record's restricted classification to be correct. This tolerates one ordinary extraction miss in a tiny four-record set but no privacy-label miss. The real run scored 4/4 (100%), all restricted checks correct, exit 0. The runner writes predictions, per-record checks, errors, model, timestamp, and summary to `eval/golden_set_results.json` even if the threshold fails; literal terminal output is in `TERMINAL_LOG.md`.

### Non-obvious choices

The historical pre-fix introduction trace used isolated SQLite data when seeded PostgreSQL access was unavailable. It is retained only as original-code evidence. The replacement trace uses seeded PostgreSQL. Part 3's prompt was designed after reading the nine actual seeded `ConversationMessage` rows and the four labeled golden records: they include financing needs/offers, uncertain future plans, activity interests, therapy/anxiety/clinical context, and a mixed health-plus-venue-preference message. The prompt therefore avoids invented facts, assigns lower confidence to uncertain plans, and treats health/clinical/psychometric facts as restricted. I used the existing `httpx` dependency and OpenAI's strict structured JSON output rather than add an SDK dependency; the service is still a real Responses API call, and tests override only the extractor dependency. The four demo messages were appended as new conversation rows for a seeded member because the original seeded messages were already processed; no original seed rows or seed script were edited. The demo persisted only the pipeline's ordinary attribute output. The deterministic sensitive-term override is deliberately conservative: it may withhold a harmless preference from a mixed message rather than risk a health disclosure.

## Part 4a — grounded introduction reasons

The existing introduction route now filters by the caller's club, `MemberAttribute.restricted.is_(False)`, and `MemberAttribute.confidence > settings.introduction_min_confidence` before constructing *both* the reason and `used_attributes` audit list from those same rows. The threshold is configured by `INTRODUCTION_MIN_CONFIDENCE` (default 0.7, validated within 0–1); equality is excluded because the requirement says above the threshold. If either member has no eligible attribute, the response is exactly `{"reason_text": "insufficient basis for an introduction", "used_attributes": []}`. The reason deliberately lists grounded facts without asserting that they are a “good match,” which the available attributes do not prove. Audit entries include attribute and member IDs, kind, text, and confidence, allowing a reviewer to identify every source row; restricted and below-threshold rows never enter either response field. The seeded PostgreSQL demo verified a business need/offer pair and a restricted-only member; focused and full tests passed.

## Closing question

**What was deliberately left out, and what would one more day add?** I did not add a schema migration for completed-empty extraction markers, a durable LLM request ledger, or automatic reconciliation for payment-provider outcomes lost after a process crash. Part 4a is implemented; Part 4b is not attempted. With one more day I would ask the schema owner for an empty-result processing marker, add a broader privacy/red-team eval (especially euphemisms and mixed messages), and implement a payment reconciliation workflow. I would then rerun the real eval and seeded-data demo after those changes.
